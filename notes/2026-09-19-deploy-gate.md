# 2026-09-19 部署被保護閘門誤擋

[← 06 開發筆記](../06-dev-notes.md) · [目錄](../README.md)

只改了 `package.json` 裡 3 行開發用的指令，自動部署就被自己的安全機制擋下。

## 背景

入隧前合併到 `main` 之後會自動部署：CI 測試全過、打包成固定的部署包、送到主機暫存、切換成新版、從外部驗收。

這條流程中有一道**保護閘門**。主機上有一份只有 root 能改的設定檔，記錄 17 個重要檔案的指紋（sha256）。這些檔案決定主機怎麼運作：

| 類別 | 例子 |
|---|---|
| 套件與依賴 | `package.json`、`pnpm-lock.yaml` |
| 資料處理 | Collector 主程式、資料庫存取 |
| 服務設定 | 五個 systemd 設定檔 |
| 維運程式 | Observer、備份程式 |

部署包裡這些檔案的指紋，只要有一個跟主機記錄的不同，部署就停下來。設計原則是：這些檔案的變更要由人審查，主機上的記錄由管理員用 root 更新，**部署流程不能自己放行自己**。

## 症狀

- 9/15：#38 重做顏色系統，順便在 `package.json` 修改 1 行、新增 2 行開發用的指令。套件依賴沒有變。
- 9/19：把 dev 發布到 main（#39），自動部署在保護閘門停下，錯誤訊息如下：

```
Protected runtime inputs changed; reviewed host maintenance is required before upload
```

修改在 dev 上已經 4 天、測試全過，但要到發布時才第一次碰到主機上的閘門。

## 定位

錯誤訊息沒說是哪個檔案，所以把 17 個受保護檔案逐一跟上線版本比對，找出只有 `package.json` 不同。

比對前要先 `git fetch`。本機沒有要比對的那個版本時，`git diff` 會把所有檔案都誤報成「有變」。

## 原因

`package.json` 除了套件依賴，還定義應用程式的名稱、版本、描述、授權、開發用的指令（scripts）等資訊。我們不希望改動的是套件依賴，也就是應用程式的執行環境；但閘門比對的是**整個檔案**的指紋，裡面任何一項改了，指紋就不同。

這次只改了 scripts，不影響主機。依賴有沒有變，其實已經由同在清單上的 `pnpm-lock.yaml` 把關，而它沒有變。所以這是**誤擋**：閘門照設計運作，只是檢查範圍比實際需要的大。

## 解決

切換版本的那一刻，閘門會同時檢查正在跑的舊版和要換上的新版，所以主機上的記錄要改兩處：

1. 把 `package.json` 的主要記錄換成新指紋，讓新版通過。
2. 在舊版的例外清單登記舊指紋，讓舊版在切換時也通過。

只改第 1 處的話，新版能進暫存，但切換時舊版對不上新記錄，會再失敗一次。這份例外清單本來就有一筆 9/11 的前例，用的是同一種做法。

記錄指紋的設定檔只有 root 能改，這是刻意的設計：如果部署流程能自己更新記錄，等於自己核准自己，閘門就沒有意義。當時 Claude Code 的安全機制也擋下了用 SSH 把腳本送到正式主機執行。所以分工是：

1. AI 寫好維護腳本。
2. 我把腳本傳到主機上，用 root 親自執行。

腳本預設只模擬（dry-run），修改前後都會檢查、會先備份、整份檔案一次寫入，任何一步失敗就自動還原。

## 驗證

腳本執行後，用主機上的部署狀態指令確認記錄已更新。

## 事後

更好的做法是把 `package.json` 的檢查範圍縮小，只看依賴相關的欄位，依賴本身仍由 `pnpm-lock.yaml` 把關。這樣安全性不降低，也能避免同樣的誤擋。

當時我決定先不改，理由是：

- **先設清楚問題的邊界**：我知道根本原因在閘門的設計，但當下最重要的是讓服務上線，根本原因另外處理。
- **改安全機制需要很多來回決策**：當時的環境不允許我投入足夠的專注力，把情況理解清楚再做好判斷。
- **重要但不緊急**：這個機制的問題是限制太多，不是限制太少。限制太多只會多一道手續，不會造成損害。

這項改進到目前還沒有做。
